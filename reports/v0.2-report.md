# FaithfulAgent v0.2 — Completion Report

_Generated 2026-03-27_

---

## 1. Executive Summary

FaithfulAgent v0.2 extends the v0.1 reference hallucination detector with a **cross-claim consistency engine**. v0.1 checks each extracted claim against the tool data that produced it — each claim is evaluated in isolation, and a response can receive a clean pass even when its claims contradict each other. v0.2 adds a new pipeline stage, `cross_checker/`, that checks whether the agent's claims are internally consistent: do comparison claims hold when their referenced values are compared? Do ranking claims reflect the actual values present in the output? Do stated totals equal the sum of their components?

No LLM is involved in the cross-claim verification path. The entire cross-checker is pure Python: float arithmetic, list operations, and `math.isclose`.

---

## 2. What Changed from v0.1

### New Pipeline Stage

v0.1's pipeline was:

```
Normalizer → Parser → Comparator → Reporter
```

v0.2 inserts a new stage between Comparator and Reporter:

```
Normalizer → Parser → Comparator → CrossChecker → Reporter
```

The CrossChecker receives the claim list, constraint list, and match results from the Comparator. It verifies each constraint independently and produces a `list[CrossClaimResult]`, which the Reporter incorporates into the final verdict.

### Changes to Existing Modules

| Module | What Changed |
|---|---|
| `schemas.py` | Added `Constraint` and `CrossClaimResult` Pydantic models. Added `cross_claim_violations: int` to `ReportSummary` and `cross_claim_results: list[CrossClaimResult]` to `Report`. No existing models were modified. |
| `config.py` | Added `CrossClaimCheckConfig` (with `enabled: bool` and `sum_tolerance: float`). Added `cross_claim: CrossClaimCheckConfig` to `VerifyConfig`. Updated `from_dict()` to accept a `"cross_claim"` key. No existing config fields were modified. |

## 3. What v0.2 Added

### New Package: `cross_checker/`

| Module | Description |
|---|---|
| `cross_checker/__init__.py` | `check_cross_claims()` entry point. Builds a `claim_id → float` value map from extracted claims and dispatches each constraint to the appropriate checker function. Short-circuits to `[]` when `config.enabled == False`. |
| `cross_checker/constraint_checker.py` | Pure constraint verification functions: `check_comparison()`, `check_ranking()`, `check_sum()`. Each takes a `Constraint`, a value map, and mode; sets `match_confidence`/`severity` based on mode; returns a `CrossClaimResult`. Includes shared `_coercion_failure_result()` helper for claims that cannot be parsed to float. |

### Three Cross-Claim Check Types

#### 1. Comparison Check (strict mode only in v0.2)

Verifies that a declared ordered relationship between two claims holds.

- **Operators:** `<`, `>`, `<=`, `>=`, `==`
- **Verification:** Coerce both `extracted_value` fields to float. Evaluate `A_value op B_value`. Equality uses `math.isclose(rel_tol=0, abs_tol=1e-9)` to guard against float representation artifacts.
- **Example:** Agent says "Flight A is cheaper" but extracted values show Flight A at ¥553 and Flight B at ¥480 → `comparison_violated`.

#### 2. Ranking Check (strict mode only in v0.2)

Verifies that a named claim's value is the minimum or maximum among a set of candidates.

- **Rank types:** `"min"`, `"max"`
- **Verification:** Coerce all candidate values. Compute actual min/max. Check that the ranked claim's value equals it (using `math.isclose`).
- **Example:** Agent says "Hotel A is the most affordable" ($200/night) but Hotel B is $150/night → `ranking_violated`.

#### 3. Sum Consistency Check (strict and heuristic modes)

Verifies that a total claim's value equals the sum of its component claims.

- **Verification:** Compute `component_sum = sum(components)`. Pass if `abs(relative_delta) < sum_tolerance` (default 1%). Zero-total edge case falls back to absolute check.
- **Example:** Agent says "Total: $900" but flights ($340) + hotel ($450) + transfers ($60) = $850 → `sum_mismatch`.

### Heuristic Mode: Sum Detection

Heuristic mode gained automatic sum constraint detection. After the existing claim extraction (unchanged), a second pass scans the text for trigger keywords:

- Case-insensitive: `total`, `grand total`, `subtotal`, `sum`, `overall cost`, `combined`
- Each must be followed or preceded by a numeric value

For each match, the parser finds the corresponding claim, collects all other numeric/currency claims as components, and builds a `Constraint(constraint_type="sum")`. Constraints are always built when the pattern matches — the parser does not check whether the math is correct.

**Heuristic sum constraints produce `severity="warning"` and `match_confidence="medium"`.** They trigger `verdict="warn"` at most, never `"fail"`, because the constraint was inferred rather than declared.

### Strict Mode: Annotation Format Extended

The v0.1 annotation format gains an optional `constraints` array:

```json
{
  "text": "Hotel A: $200. Hotel B: $150. Hotel C: $220.",
  "refs": [
    {"span": [10, 13], "call_id": "call_hotels", "path": "$.hotel_a.price"},
    {"span": [25, 28], "call_id": "call_hotels", "path": "$.hotel_b.price"},
    {"span": [40, 43], "call_id": "call_hotels", "path": "$.hotel_c.price"}
  ],
  "constraints": [
    {
      "constraint_id": "rank_1",
      "constraint_type": "ranking",
      "rank_type": "min",
      "ranked_ref_index": 0,
      "candidate_ref_indices": [0, 1, 2]
    }
  ]
}
```

Constraints reference `refs` by 0-based index. The strict parser maps these to `claim_id` values after building the claim list. If the `constraints` key is absent, the pipeline runs with no cross-claim checks — identical to v0.1 behavior.

### Verdict Logic Updated

| Condition | Verdict |
|---|---|
| Any `MatchResult.status == "error"` OR any `CrossClaimResult` with `status="error"` and `severity="error"` | `"fail"` |
| No fail conditions, but any `MatchResult.status == "warning"` OR any `CrossClaimResult` with `status="error"` and `severity="warning"` | `"warn"` |
| None of the above | `"pass"` |

`summary.cross_claim_violations` counts all `CrossClaimResult` entries where `status="error"`, regardless of severity. It does **not** contribute to `passed`/`warnings`/`errors` — those counters remain `MatchResult`-only.

## 4. Public API

### `verify()` Signature (unchanged)

```python
from faithfulagent import verify

report = verify(
    agent_output="...",
    tool_calls=[...],
    mode="strict",              # "strict" or "heuristic"
    source_format="raw",        # "raw", "openai", or "langchain"
    checks={
        "numeric": {"tolerance": 0.05},
        "cross_claim": {"enabled": True, "sum_tolerance": 0.01},  # NEW in v0.2
    }
)
```

### Report Schema (extended)

```python
Report(
    verification_id: str,
    timestamp: datetime,
    mode: "strict" | "heuristic",
    summary: ReportSummary(
        total_claims: int,
        passed: int,
        warnings: int,
        errors: int,
        cross_claim_violations: int,       # NEW — count of CrossClaimResult with status="error"
        verdict: "pass" | "warn" | "fail"
    ),
    claims: list[MatchResult],
    cross_claim_results: list[CrossClaimResult]  # NEW — empty when no constraints exist
)
```

### `CrossClaimResult` Schema

```python
CrossClaimResult(
    constraint_id: str,
    constraint_type: "comparison" | "ranking" | "sum",
    status: "pass" | "error",
    violation_category: "comparison_violated" | "ranking_violated" | "sum_mismatch" | None,
    severity: "error" | "warning",          # "error" = strict mode, "warning" = heuristic mode
    match_confidence: "high" | "medium",    # "high" = strict, "medium" = heuristic
    involved_claim_ids: list[str],
    observed_values: dict[str, Any],        # claim_id → coerced float value
    expected_relationship: str,             # e.g., "553.0 < 480.0" or "sum=850.0, total=900.0"
    diff: dict | None,                      # violation details; structure varies by type
    recommended_action: str | None
)
```

## 8. Design Decisions

### Why a new `cross_checker/` package rather than extending `comparator/`

The comparator is claim-to-tool-data. Cross-claim checking is claim-to-claim. They operate on different inputs, have different error semantics (`MatchResult` vs `CrossClaimResult`), and serve different purposes in the pipeline. Keeping them separate preserves single-responsibility and makes both independently testable.

### Why `CrossClaimResult` is separate from `MatchResult`

`MatchResult` carries tool-data-specific fields (`matched_call_id`, `matched_field`, `expected_value`, `observed_value`) that have no meaning for cross-claim checks. A dedicated model avoids nullable field confusion and keeps the reporter's counting logic clean.

### Why heuristic mode only detects sums, not rankings or comparisons

Ranking and comparison detection in free text requires identifying the subject of the comparison, its attribute, and its relationship to other claims. This requires dependency parsing (excluded by design), a curated phrase list (fragile), or an LLM (excluded by principle). Sum detection requires only a total-labeled number and arithmetic — high enough signal-to-noise ratio to ship.

### Why no graph library (networkx)

v0.2 constraints are flat — each constraint references 2–N claims, but constraints are independent of each other. A plain `list[Constraint]` iterated in `check_cross_claims()` is sufficient. Graph-based constraint analysis is deferred to v0.3 (dependency graph validation).

### Why no new dependencies

The entire cross-checker is pure Python: `math.isclose`, `float`, list operations. No external library was needed. This keeps the install footprint unchanged from v0.1.

## 9. Known Limitations

**Heuristic mode cross-claim coverage is narrow.** Only sum constraints are detected. Rankings ("cheapest", "fastest") and comparisons ("A is cheaper than B") require NLP beyond regex and are deferred. Users who need full cross-claim checking must use strict mode.

**Heuristic sum detection has false positive risk.** Unrelated numeric claims (years, quantities, room numbers) are included as components. If `sum(all_others)` coincidentally equals the total, no false positive occurs; if it doesn't, a spurious `sum_mismatch` is reported. Mitigated by requiring a trigger keyword and by setting `severity="warning"` (never triggers `"fail"`).

**No evaluation benchmark.** The PRD specifies precision/recall targets (strict: 100%/100%, heuristic sum: >90%/>70%) but the benchmark dataset has not been constructed. Accuracy claims are based on unit tests with synthetic data only.

**CI/CD still absent.** Tests run locally only, same as v0.1.

**`cross_checker/__init__.py` coverage at 84%.** Below the per-module ideal but above the 90% overall floor. The uncovered lines are defensive error handling for invalid types that Pydantic validators prevent at construction time.

## 10. What's Next

### v0.3 — Dependency Graph Validation

v0.2 checks whether claims are consistent with each other. v0.3 checks whether the *relationships between claims* form a valid dependency chain — if a foundational claim fails, all downstream claims that depend on it should be flagged.

**Problem v0.3 solves:** An agent response contains "Flight A costs $553 (from API). The tax is 10% of the fare, so $55.30. Total with tax: $608.30." v0.2 can verify the sum ($553 + $55.30 = $608.30 ✓) and the individual values against tool data. But if the $553 claim is wrong (tool actually returned $500), v0.2 marks the $553 claim as failed while the $55.30 and $608.30 claims may still pass their individual checks — even though they were derived from the incorrect base value. v0.3 builds a DAG of claim dependencies and propagates failure downstream: if $553 fails, $55.30 and $608.30 are automatically tainted.

**Key deliverables:**
- Dependency edge declarations in the `constraints` array (new constraint type or extension)
- DAG construction from claim relationships
- Failure propagation algorithm
- Updated `CrossClaimResult` to indicate upstream failure vs direct failure
